1. Pods: Contenedores y Ciclo de Vida

Namespace: lab-pods

El Pod es la unidad mínima ejecutable en Kubernetes. En este bloque se profundiza en patrones multi-contenedor (Sidecar), inicialización secuencial con InitContainers y mecanismos avanzados de detección de fallos y preparación (Probes).

Ejercicio 1.1: Pod Multi-contenedor con Volumen Compartido (Patrón Sidecar)

Intermedio

Escenario: El equipo de desarrollo ha diseñado un servicio web ligero que genera logs continuos en un archivo local. Para cumplir las políticas de monitorización corporativas, se necesita un contenedor auxiliar (sidecar) que lea esos registros en tiempo real y los procese, sin modificar la imagen base de la aplicación.

Requerimientos Técnicos:

  • Crear el namespace lab-pods si no existe previamente.
  • Crear un Pod con nombre pod-sidecar-logger en el namespace lab-pods.
  • El Pod debe montar un volumen en memoria compartida de tipo emptyDir: {} en la ruta /var/log/app en ambos contenedores.
  • Contenedor primario (app): Imagen busybox:1.36. Debe ejecutar un bucle en segundo plano escribiendo la fecha actual y un mensaje cada 5 segundos en /var/log/app/events.log.
  • Contenedor secundario (sidecar): Imagen busybox:1.36. Debe monitorear continuamente el archivo con tail -f /var/log/app/events.log.
Verificación Esperada

Ejecutar kubectl logs -n lab-pods pod-sidecar-logger -c sidecar y comprobar que aparecen las líneas de log generadas por el contenedor principal en intervalos de 5 segundos.

Ejercicio 1.2: Inicialización con InitContainer para Validación de Dependencias

Intermedio

Escenario: Una API de negocio no debe arrancar hasta que su base de datos o servicio dependiente responda por red. De lo contrario, la aplicación colapsará con errores de conexión.

Requerimientos Técnicos:

  • Crear un Pod llamado pod-backend-init en el namespace lab-pods.
  • Incluir un initContainer llamado wait-db con imagen busybox:1.36 que use nc -z -w 2 db-service 3306 en un bucle con retardo de 3 segundos hasta que el host y puerto respondan.

  • Probar el estado del Pod antes y después de simular el servicio dependiente con un Pod/Service temporal.
Verificación Esperada

Al crear el Pod, debe permanecer en estado Init:0/1. Tras crear el servicio y pod temporal db-service en el puerto 3306, el Pod debe transicionar automáticamente a PodInitializing y luego a Running (1/1).

Ejercicio 1.3: Resiliencia Avanzada con Startup, Liveness y Readiness Probes

Nivel CKA

Escenario: En entornos de producción, una aplicación con carga pesada tarda 20 segundos en cargar sus cachés en memoria. Si se usan únicamente sondas Liveness agresivas, Kubelet matará el contenedor antes de terminar de arrancar, entrando en CrashLoopBackOff. Se debe diseñar una estrategia completa de tres sondas.

Requerimientos Técnicos:

  • Crear un Pod con nombre pod-health-hardened en el namespace lab-pods.
  • Contenedor: imagen nginx:1.25-alpine, puerto de contenedor 80.
  • Configurar startupProbe HTTP en path: /, port: 80, con failureThreshold: 10 y periodSeconds: 5 (hasta 50 segundos de ventana de arranque).
  • Configurar livenessProbe HTTP en path: /, port: 80, con periodSeconds: 10, failureThreshold: 3.
  • Configurar readinessProbe HTTP en path: /, port: 80, con periodSeconds: 5, successThreshold: 1, failureThreshold: 2.
Verificación Esperada

Ejecutar kubectl describe pod -n lab-pods pod-health-hardened y verificar que las 3 sondas aparecen registradas y que no hay reinicios (Restarts: 0). Simular un fallo renombrando index.html y observar cómo el Pod deja de estar Ready y luego se reinicia.

2. ReplicaSets: Controladores de Réplicas y Auto-sanación

Namespace: lab-replicasets

El ReplicaSet garantiza que un número específico de réplicas de Pods idénticos se encuentren en ejecución en cualquier momento. Se evalúa el funcionamiento de sus selectores basados en conjuntos, la auto-sanación y la gestión de Pods huérfanos.

Ejercicio 2.1: Selectores Basados en Conjuntos (matchExpressions) y Adopción de Pods

Intermedio

Escenario: Un equipo ha desplegado manualmente dos Pods etiquetados para pre-producción. Se debe crear un ReplicaSet con selectores avanzados que adopte automáticamente dichos Pods y complete las réplicas restantes.

Requerimientos Técnicos:

  • Crear el namespace lab-replicasets.
  • Crear manualmente un Pod llamado legacy-pod-1 con etiquetas app: payment, tier: backend, env: staging.
  • Crear un ReplicaSet llamado rs-payment-processor con replicas: 3.
  • El selector del ReplicaSet debe usar matchExpressions: app In [payment] y env In [staging, production].
  • La plantilla de Pods (template) debe generar Pods con imagen nginx:1.25-alpine y las etiquetas correspondientes.
Verificación Esperada

Ejecutar kubectl get pods -n lab-replicasets --show-labels y verificar que el ReplicaSet sólo creó 2 Pods nuevos porque adoptó a legacy-pod-1, sumando 3 réplicas en total.

3. Deployments: Actualizaciones Continuas y Estrategias Rollout

Namespace: lab-deployments

Los Deployments gestionan ReplicaSets de forma declarativa y permiten actualizaciones sin caída de servicio (RollingUpdate), pausas, revisiones históricas y rollback instantáneo.

Ejercicio 3.1: Despliegue Declarativo con Requests y Limits de Recursos

Intermedio

Escenario: Para garantizar la estabilidad del clúster y evitar el efecto 'vecino ruidoso' (noisy neighbor), todos los Pods de la aplicación web deben declarar explícitamente sus peticiones mínimas y techos de memoria y CPU.

Requerimientos Técnicos:

  • Crear el namespace lab-deployments.
  • Crear un Deployment llamado deploy-web-secured con 3 réplicas e imagen nginx:1.25-alpine.

  • Configurar resources.requests: 64Mi de memoria y 50m de CPU.
  • Configurar resources.limits: 128Mi de memoria y 100m de CPU.
  • El contenedor debe exponer el puerto 80 con nombre http.
Verificación Esperada

Ejecutar kubectl get deployment -n lab-deployments deploy-web-secured -o jsonpath='{.spec.template.spec.containers[0].resources}' y comprobar que los límites y peticiones coinciden exactamente.

Ejercicio 6.2: Montaje de Secret como Volumen con Permisos Restringidos (0400)

Nivel CKA

Escenario: Una clave privada SSH o API Key debe montarse como archivo en `/etc/keys/api-key.pem`. Por auditoría de seguridad bancaria, el archivo debe ser de solo lectura para el propietario (`chmod 400`), bloqueando el acceso a otros usuarios.

Requerimientos Técnicos:

  • Montar el Secret en un Pod pod-restricted-secret en la ruta /etc/keys.

1. Soluciones Técnicas: Pods: Contenedores y Ciclo de Vida

Namespace: lab-pods

Solución 1.1: Solución: Pod Multi-contenedor con Volumen Compartido (Patrón Sidecar)

← Volver al Enunciado

Explicación Técnica: Los contenedores dentro de un mismo Pod comparten el espacio de red (misma IP y localhost) y pueden compartir almacenamiento montando el mismo volumen. Un volumen emptyDir se crea vacío al instanciarse el Pod en el nodo y permanece vivo mientras el Pod exista.

Manifiesto Declarativo YAML:

apiVersion: v1
kind: Namespace
metadata:
  name: lab-pods
---
apiVersion: v1
kind: Pod
metadata:
  name: pod-sidecar-logger
  namespace: lab-pods
  labels:
    app: multi-container-demo
spec:
  volumes:
    - name: shared-logs
      emptyDir: {}
  containers:
    - name: app
      image: busybox:1.36
      command: ["/bin/sh", "-c"]
      args:
        - |
          while true; do
            echo "$(date '+%T') Evento en app" >> /var/log/app/events.log;
            sleep 5;
          done
      volumeMounts:
        - name: shared-logs
          mountPath: /var/log/app
    - name: sidecar
      image: busybox:1.36
      command: ["/bin/sh", "-c"]
      args:
        - |
          touch /var/log/app/events.log
          tail -n +1 -f /var/log/app/events.log
      volumeMounts:
        - name: shared-logs
          mountPath: /var/log/app

Procedimiento de Validación:

# 1. Aplicar el manifiesto
kubectl apply -f pod-sidecar.yaml

# 2. Verificar que ambos contenedores estén listos (2/2)
kubectl get pods -n lab-pods pod-sidecar-logger

# 3. Comprobar que el sidecar lee los eventos emitidos por el app
kubectl logs -n lab-pods pod-sidecar-logger -c sidecar --tail=10
Tip de Examen CKA
Cuando se consultan logs de un Pod multi-contenedor, el flag -c <nombre-contenedor> es estrictamente obligatorio; de lo contrario, kubectl logs devolverá error pidiendo especificar el contenedor.

Solución 1.2: Solución: Inicialización con InitContainer para Validación de Dependencias

← Volver al Enunciado

Explicación Técnica: Los initContainers se ejecutan en orden secuencial antes de que los contenedores de la aplicación se inicien. Si un InitContainer no finaliza con código de salida 0, el Pod se reinicia según su restartPolicy y los contenedores principales nunca se ejecutan.

Manifiesto Declarativo YAML:

apiVersion: v1
kind: Pod
metadata:
  name: pod-backend-init
  namespace: lab-pods
  labels:
    tier: backend
spec:
  initContainers:
    - name: wait-db
      image: busybox:1.36
      command: ['sh', '-c']
      args:
        - |
          echo "Verificando disponibilidad de db-service:3306...";
          until nc -z -w 2 db-service 3306; do
            echo "Base de datos no alcanzable aún. Esperando 3s...";
            sleep 3;
          done;
          echo "¡Conexión establecida exitosamente!";
  containers:
    - name: backend-api
      image: nginx:1.25-alpine
      ports:
        - containerPort: 80

Validación y Simulación del Servicio Dependiente:

# 1. Crear el pod con el initContainer
kubectl apply -f pod-backend-init.yaml

# 2. Comprobar estado: Debe quedar en Init:0/1
kubectl get pod -n lab-pods pod-backend-init
kubectl logs -n lab-pods pod-backend-init -c wait-db

# 3. Simular la base de datos creando un pod y servicio temporal
kubectl run db-service --image=busybox:1.36 -n lab-pods \
  --port=3306 -- nc -lk -p 3306
kubectl expose pod db-service -n lab-pods --port=3306

# 4. Verificar que pod-backend-init transiciona a Running (1/1)
kubectl get pod -n lab-pods pod-backend-init -w
Trampa Frecuente
Si el servicio db-service se crea en otro namespace, la resolución DNS requerirá el FQDN completo: db-service.<otro-namespace>.svc.cluster.local. En este ejercicio, ambos conviven en lab-pods.

Solución 1.3: Solución: Resiliencia Avanzada con Startup, Liveness y Readiness Probes

← Volver al Enunciado

Explicación Técnica: La combinación correcta de las 3 sondas evita bucles de muerte (CrashLoop) en arranques lentos (startupProbe deshabilita liveness y readiness hasta tener éxito), asegura que el tráfico solo llegue a Pods operativos (readinessProbe) y reinicia instancias congeladas (livenessProbe).

Manifiesto Declarativo YAML:

apiVersion: v1
kind: Pod
metadata:
  name: pod-health-hardened
  namespace: lab-pods
  labels:
    app: hardened-web
spec:
  containers:
    - name: web
      image: nginx:1.25-alpine
      ports:
        - containerPort: 80
      # 1. Startup Probe: da hasta 10 * 5s = 50s para arrancar
      startupProbe:
        httpGet:
          path: /
          port: 80
        initialDelaySeconds: 2
        periodSeconds: 5
        failureThreshold: 10
      # 2. Liveness Probe: reinicia si el servicio muere tras el startup
      livenessProbe:
        httpGet:
          path: /
          port: 80
        periodSeconds: 10
        timeoutSeconds: 2
        failureThreshold: 3
      # 3. Readiness Probe: extrae el Pod de los endpoints si no está listo
      readinessProbe:
        httpGet:
          path: /
          port: 80
        periodSeconds: 5
        successThreshold: 1
        failureThreshold: 2

Validación Operativa:

# 1. Aplicar y verificar registro de sondas
kubectl apply -f pod-probes.yaml
kubectl describe pod -n lab-pods pod-health-hardened | \
  grep -E "Startup|Liveness|Readiness"

# 2. Simular fallo de readiness
kubectl exec -n lab-pods pod-health-hardened -c web -- \
  mv /usr/share/nginx/html/index.html /tmp/
# Observar que el Pod pasa a READY 0/1 sin reiniciarse inmediatamente
kubectl get pod -n lab-pods pod-health-hardened

# 3. Tras fallar la livenessProbe (3 fallos * 10s = 30s),
#    Kubelet reinicia el contenedor
kubectl get pod -n lab-pods pod-health-hardened

2. Soluciones Técnicas: ReplicaSets: Controladores de Réplicas y Auto-sanación

Namespace: lab-replicasets

Solución 2.1: Solución: Selectores Basados en Conjuntos (matchExpressions) y Adopción de Pods

← Volver al Enunciado

Explicación Técnica: Los ReplicaSets no crean réplicas si ya existen Pods cuyas etiquetas satisfacen sus selectores. El selector con matchExpressions permite reglas lógicas avanzadas con operadores In, NotIn, Exists y DoesNotExist.

Comandos y Manifiesto YAML:

# 1. Crear namespace y Pod preexistente
kubectl create namespace lab-replicasets
kubectl run legacy-pod-1 --namespace=lab-replicasets \
  --image=nginx:1.25-alpine \
  --labels="app=payment,tier=backend,env=staging"

Manifiesto del ReplicaSet:

apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: rs-payment-processor
  namespace: lab-replicasets
spec:
  replicas: 3
  selector:
    matchExpressions:
      - {key: app, operator: In, values: [payment]}
      - {key: env, operator: In, values: [staging, production]}
  template:
    metadata:
      labels:
        app: payment
        tier: backend
        env: staging
    spec:
      containers:
        - name: processor
          image: nginx:1.25-alpine
          ports:
            - containerPort: 80

Validación:

kubectl apply -f rs-payment.yaml
# Comprobar que legacy-pod-1 tiene como Controller al ReplicaSet
kubectl get pods -n lab-replicasets -l app=payment --show-labels

Solución 2.2: Solución: Escalado Elástico y Prueba de Auto-recuperación

← Volver al Enunciado

Explicación Técnica: El controlador del ReplicaSet ejecuta un bucle continuo de control (Reconciliation Loop) comparando el estado actual con el estado deseado declarado en spec.replicas.

Manifiesto YAML Base:

apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: rs-elastic-worker
  namespace: lab-replicasets
spec:
  replicas: 2
  selector:
    matchLabels:
      app: elastic-worker
  template:
    metadata:
      labels:
        app: elastic-worker
    spec:
      containers:
        - name: redis
          image: redis:7.2-alpine

Comandos Imperativos de Escalado y Prueba de Resiliencia:

# 1. Desplegar
kubectl apply -f rs-elastic.yaml

# 2. Escalar a 5 réplicas
kubectl scale rs rs-elastic-worker -n lab-replicasets --replicas=5
kubectl get pods -n lab-replicasets -l app=elastic-worker

# 3. Matar dos pods de forma simultánea
PODS_TO_DELETE=$(kubectl get pods -n lab-replicasets \
  -l app=elastic-worker \
  -o jsonpath='{.items[0..1].metadata.name}')
kubectl delete pods -n lab-replicasets $PODS_TO_DELETE

# 4. Comprobar que el número total se mantiene inmediatamente en 5
kubectl get rs -n lab-replicasets rs-elastic-worker

Solución 2.3: Solución: Aislamiento y Depuración de un Pod en Caliente (Quarantine)

← Volver al Enunciado

Explicación Técnica: Los ReplicaSets gestionan Pods basándose exclusivamente en etiquetas. Si alteramos la etiqueta de un Pod en ejecución con --overwrite, el ReplicaSet ya no lo reconocerá como suyo, lo desasociará y generará un reemplazo para volver a cumplir la cuota deseada.

Procedimiento Paso a Paso:

# 1. Desplegar el ReplicaSet inicial
cat <<EOF | kubectl apply -f -
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: rs-monitored
  namespace: lab-replicasets
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web-worker
  template:
    metadata:
      labels:
        app: web-worker
    spec:
      containers:
        - name: nginx
          image: nginx:1.25-alpine
EOF

# 2. Identificar el nombre de uno de los pods
TARGET_POD=$(kubectl get pods -n lab-replicasets \
  -l app=web-worker \
  -o jsonpath='{.items[0].metadata.name}')
echo "Aislando pod: $TARGET_POD"

# 3. Sobreescribir la etiqueta selectora para sacarlo del control del ReplicaSet
kubectl label pod $TARGET_POD -n lab-replicasets \
  app=debug-quarantine --overwrite

# 4. Verificar que existen 4 pods: 3 del RS y 1 aislado
kubectl get pods -n lab-replicasets -L app
Patrón Clave en Producción
Esta técnica es la recomendada en incidentes reales (Troubleshooting) para conectarse mediante kubectl exec a un Pod defectuoso sin que el tráfico de los usuarios continúe impactando en él.

3. Soluciones Técnicas: Deployments: Actualizaciones Continuas y Estrategias Rollout

Namespace: lab-deployments

Solución 3.1: Solución: Despliegue Declarativo con Requests y Limits de Recursos

← Volver al Enunciado

Explicación Técnica: Los requests determinan qué nodo puede alojar el Pod (scheduling), mientras que los limits son aplicados por cgroups en el kernel de Linux. Superar el límite de memoria provoca terminación inmediata por OOMKilled.

Manifiesto Declarativo YAML:

apiVersion: v1
kind: Namespace
metadata:
  name: lab-deployments
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: deploy-web-secured
  namespace: lab-deployments
  labels:
    app: web-secured
    tier: frontend
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web-secured
  template:
    metadata:
      labels:
        app: web-secured
        tier: frontend
    spec:
      containers:
        - name: nginx
          image: nginx:1.25-alpine
          ports:
            - name: http
              containerPort: 80
          resources:
            requests:
              memory: "64Mi"
              cpu: "50m"
            limits:
              memory: "128Mi"
              cpu: "100m"

Comando Imperativo Rápido (Truco CKA):

kubectl create deployment deploy-web-secured -n lab-deployments \
  --image=nginx:1.25-alpine \
  --replicas=3 --dry-run=client -o yaml > deploy.yaml
# Añadir la sección resources en el fichero generado y aplicar:
kubectl apply -f deploy.yaml

Solución 3.2: Solución: RollingUpdate Controlado con maxSurge y maxUnavailable

← Volver al Enunciado

Explicación Técnica: Con maxUnavailable: 0, Kubernetes no apagará ningún Pod existente hasta que un nuevo Pod esté completamente en estado Ready. Con maxSurge: 1, creará los nuevos Pods de uno en uno.

Manifiesto Declarativo YAML:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: deploy-rolling-tuned
  namespace: lab-deployments
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  selector:
    matchLabels:
      app: rolling-tuned
  template:
    metadata:
      labels:
        app: rolling-tuned
    spec:
      containers:
        - name: httpd
          image: httpd:2.4-alpine
          ports:
            - containerPort: 80

Actualización y Seguimiento:

# 1. Aplicar el deployment base
kubectl apply -f deploy-rolling.yaml

# 2. Actualizar la imagen imperativamente
kubectl set image deployment/deploy-rolling-tuned \
  httpd=httpd:2.4.58-alpine -n lab-deployments

# 3. Seguir el progreso del despliegue paso a paso
kubectl rollout status deployment/deploy-rolling-tuned -n lab-deployments

Solución 3.3: Solución: Simulación de Release Fallida y Rollback a Revisión Específica

← Volver al Enunciado

Explicación Técnica: Kubernetes almacena el historial de revisiones creando un ReplicaSet nuevo para cada cambio en el template de Pods. Si una nueva versión falla, la versión anterior permanece en ejecución hasta que la nueva alcance el estado Ready, protegiendo a los usuarios finales.

Procedimiento Completo de Fallo y Rollback:

# 1. Crear despliegue inicial estable
kubectl create deployment deploy-ecommerce -n lab-deployments \
  --image=nginx:1.24-alpine --replicas=3
kubectl annotate deployment/deploy-ecommerce -n lab-deployments \
  kubernetes.io/change-cause="Version 1.0 estable"

# 2. Provocar el fallo con imagen errónea
kubectl set image deployment/deploy-ecommerce \
  nginx=nginx:v999.invalid -n lab-deployments
kubectl annotate deployment/deploy-ecommerce -n lab-deployments \
  kubernetes.io/change-cause="Update fallido v999"

# 3. Comprobar que los nuevos pods quedan bloqueados
kubectl get pods -n lab-deployments -l app=deploy-ecommerce

# 4. Inspeccionar el historial
kubectl rollout history deployment/deploy-ecommerce -n lab-deployments

# 5. Ejecutar Rollback a la revision 1
kubectl rollout undo deployment/deploy-ecommerce \
  -n lab-deployments --to-revision=1

# 6. Comprobar resolucion exitosa
kubectl rollout status deployment/deploy-ecommerce -n lab-deployments
kubectl get deployment -n lab-deployments deploy-ecommerce -o wide

Solución 4.1: Solución: Servicio ClusterIP con Desacoplamiento de Puertos y Endpoints

← Volver al Enunciado

Explicación Técnica: El objeto Service abstrae los Pods mediante etiquetas. El campo port es el puerto expuesto en el clúster por el Service, mientras que targetPort es el puerto real en el que escucha el contenedor dentro del Pod.

Manifiesto YAML:

apiVersion: v1
kind: Namespace
metadata:
  name: lab-services
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: deploy-api-node
  namespace: lab-services
spec:
  replicas: 2
  selector:
    matchLabels:
      app: api-node
  template:
    metadata:
      labels:
        app: api-node
    spec:
      containers:
        - name: echo
          image: hashicorp/http-echo:latest
          args:
            - "-text=Respuesta de API"
            - "-listen=:3000"
          ports:
            - containerPort: 3000
---
apiVersion: v1
kind: Service
metadata:
  name: svc-api-node
  namespace: lab-services
spec:
  type: ClusterIP
  selector:
    app: api-node
  ports:
    - name: http
      port: 80
      targetPort: 3000

Solución 4.2: Solución: Exposición Externa mediante Servicio NodePort en Puerto Fijo

← Volver al Enunciado

Explicación Técnica: Un servicio NodePort asigna un puerto en el rango 30000-32767 en todas las interfaces de red de cada nodo del clúster (Worker y Control Plane). Kube-proxy enruta los paquetes entrantes al NodePort hacia los Pods correspondientes.

Manifiesto YAML:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-admin
  namespace: lab-services
spec:
  replicas: 2
  selector:
    matchLabels:
      app: web-admin
  template:
    metadata:
      labels:
        app: web-admin
    spec:
      containers:
        - name: nginx
          image: nginx:1.25-alpine
          ports:
            - containerPort: 80
---
apiVersion: v1
kind: Service
metadata:
  name: svc-admin-nodeport
  namespace: lab-services
spec:
  type: NodePort
  selector:
    app: web-admin
  ports:
    - port: 80
      targetPort: 80
      nodePort: 30088

Verificación:

# 1. Aplicar manifiesto
kubectl apply -f svc-nodeport.yaml

# 2. Obtener la IP de un nodo
NODE_IP=$(kubectl get nodes \
  -o jsonpath='{.items[0].status.addresses[?(@.type=="InternalIP")].address}')
echo "Probando en: http://$NODE_IP:30088"

# 3. Realizar petición HTTP
curl -I http://$NODE_IP:30088

Solución 4.3: Solución: Headless Service (clusterIP: None) y Resolución DNS Directa

← Volver al Enunciado

Explicación Técnica: Al declarar clusterIP: None, Kubernetes no reserva ninguna IP virtual en el rango de servicios ni crea reglas de proxy en iptables/IPVS. CoreDNS responde a las peticiones del nombre del servicio devolviendo directamente la lista de IPs de los Pods asociados.

Manifiesto YAML:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: deploy-cluster-members
  namespace: lab-services
spec:
  replicas: 3
  selector:
    matchLabels:
      role: member
  template:
    metadata:
      labels:
        role: member
    spec:
      containers:
        - name: web
          image: nginx:1.25-alpine
          ports:
            - containerPort: 80
---
apiVersion: v1
kind: Service
metadata:
  name: svc-headless
  namespace: lab-services
spec:
  clusterIP: None
  selector:
    role: member
  ports:
    - port: 80
      targetPort: 80

Inspección DNS con nslookup:

# 1. Aplicar
kubectl apply -f svc-headless.yaml

# 2. Consultar DNS desde un pod temporal con dnsutils
kubectl run dns-test --rm -it -n lab-services \
  --image=registry.k8s.io/e2e-test-images/jessie-dnsutils:1.3 -- \
  nslookup svc-headless.lab-services.svc.cluster.local

# Observar que la respuesta contiene las 3 IPs de los pods (Address 1, Address 2, Address 3)
Uso en StatefulSets
Los Headless Services son un requisito indispensable para los StatefulSets, ya que permiten resolver a cada Pod individual por su nombre canónico (ej: web-0.svc-headless, web-1.svc-headless).

5. Soluciones Técnicas: ConfigMaps: Desacoplamiento de la Configuración

Namespace: lab-configmaps

Solución 5.1: Solución: Inyección de Parámetros como Variables de Entorno (individuales y envFrom)

← Volver al Enunciado

Explicación Técnica: La directiva envFrom importa automáticamente todas las claves de un ConfigMap como variables de entorno. Cuando se necesita renombrar la variable o extraer una sola clave, se utiliza valueFrom.configMapKeyRef.

Manifiesto YAML:

apiVersion: v1
kind: Namespace
metadata:
  name: lab-configmaps
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: cm-app-config
  namespace: lab-configmaps
data:
  APP_ENV: "production"
  LOG_LEVEL: "info"
  MAX_CONNECTIONS: "100"
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: cm-feature-flags
  namespace: lab-configmaps
data:
  BETA_FEATURE: "true"
---
apiVersion: v1
kind: Pod
metadata:
  name: pod-config-env
  namespace: lab-configmaps
spec:
  containers:
    - name: app
      image: busybox:1.36
      command: ["/bin/sh", "-c", "env && sleep 3600"]
      # Importación masiva
      envFrom:
        - configMapRef:
            name: cm-app-config
      # Importación individual
      env:
        - name: BETA_FEATURE
          valueFrom:
            configMapKeyRef:
              name: cm-feature-flags
              key: BETA_FEATURE

Validación:

kubectl apply -f cm-env.yaml
kubectl exec -n lab-configmaps pod-config-env -- printenv | grep -E "APP_ENV|LOG_LEVEL|MAX_CONNECTIONS|BETA_FEATURE"

Solución 5.2: Solución: Montaje de Archivos de Configuración Completos mediante Volumen

← Volver al Enunciado

Explicación Técnica: Cada clave del diccionario data en un ConfigMap se convierte en un archivo con el mismo nombre dentro del directorio donde se monta el volumen. Las actualizaciones del ConfigMap se sincronizan automáticamente en el Pod cuando se monta como volumen (a diferencia de las variables de entorno, que son estáticas al arranque).

Manifiesto YAML:

apiVersion: v1
kind: ConfigMap
metadata:
  name: cm-nginx-conf
  namespace: lab-configmaps
data:
  custom.conf: |
    server {
        listen 8080;
        location / {
            add_header X-Custom-Header "K8s-Course" always;
            return 200 "Configuracion inyectada exitosamente\n";
        }
    }
---
apiVersion: v1
kind: Pod
metadata:
  name: pod-nginx-custom
  namespace: lab-configmaps
spec:
  volumes:
    - name: nginx-config-vol
      configMap:
        name: cm-nginx-conf
  containers:
    - name: nginx
      image: nginx:1.25-alpine
      ports:
        - containerPort: 8080
      volumeMounts:
        - name: nginx-config-vol
          mountPath: /etc/nginx/conf.d

Validación:

kubectl apply -f cm-volume.yaml
# Probar la respuesta HTTP y verificar cabecera
kubectl exec -n lab-configmaps pod-nginx-custom -- wget -S -O - http://localhost:8080

Solución 5.3: Solución: Montaje Granular con subPath sin Sobreescribir Directorios

← Volver al Enunciado

Explicación Técnica: La directiva subPath monta un archivo específico del volumen en lugar de todo el volumen como un directorio. Esto evita el 'enmascaramiento' (shadowing) de los archivos preexistentes en la imagen del contenedor.

Manifiesto YAML:

apiVersion: v1
kind: ConfigMap
metadata:
  name: cm-single-file

Solución 6.3: Solución: Secret de Certificado TLS (kubernetes.io/tls) para Servidor Seguro

← Volver al Enunciado

Explicación Técnica: El tipo kubernetes.io/tls valida automáticamente que los datos proporcionados correspondan a una clave privada y un certificado X.509 válidos (claves tls.crt y tls.key). Para servir HTTPS, montamos el Secret como volumen en /etc/nginx/certs y configuramos Nginx para responder en el puerto 443 usando dichos certificados.

Paso 1: Generación del Certificado y Creación del Secret TLS:

# 1. Generar par de certificados SSL autofirmados para test.local
openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
  -keyout /tmp/tls.key -out /tmp/tls.crt -subj "/CN=test.local/O=k8s-lab"

# 2. Crear el Secret nativo TLS en Kubernetes
kubectl create secret tls sec-tls-cert -n lab-secrets \
  --cert=/tmp/tls.crt \
  --key=/tmp/tls.key

# 3. Comprobar metadata y formato del secret
kubectl get secret -n lab-secrets sec-tls-cert -o yaml

Paso 2: Manifiesto del Pod Nginx con SSL (pod-tls-web.yaml):

apiVersion: v1
kind: Pod
metadata:
  name: pod-tls-web
  namespace: lab-secrets
spec:
  volumes:
    - name: certs-vol
      secret:
        secretName: sec-tls-cert
  containers:
    - name: nginx-ssl
      image: nginx:1.25-alpine
      command:
        - /bin/sh
        - -c
        - |
          cat << 'EOF' > /etc/nginx/conf.d/ssl.conf
          server {
              listen 443 ssl;
              server_name test.local;
              ssl_certificate /etc/nginx/certs/tls.crt;
              ssl_certificate_key /etc/nginx/certs/tls.key;
              location / {
                  return 200 'Conexion TLS Segura con Secret Exitosa\n';
              }
          }
          EOF
          exec nginx -g 'daemon off;'
      ports:
        - containerPort: 443
      volumeMounts:
        - name: certs-vol
          mountPath: /etc/nginx/certs
          readOnly: true

Paso 3: Despliegue y Validación con curl:

# 1. Desplegar el Pod Nginx con SSL
kubectl apply -f pod-tls-web.yaml

# 2. Esperar a que el Pod esté en estado Running y obtener su IP
kubectl wait --for=condition=Ready pod/pod-tls-web -n lab-secrets --timeout=30s
POD_IP=$(kubectl get pod -n lab-secrets pod-tls-web \
  -o jsonpath='{.status.podIP}')

# 3. Petición HTTPS con curl verificando el certificado generado
curl --cacert /tmp/tls.crt --resolve test.local:443:$POD_IP \
  https://test.local/
# Salida esperada: Conexion TLS Segura con Secret Exitosa

# 4. Alternativa de verificación rápida dentro del contenedor
kubectl exec -n lab-secrets pod-tls-web -- \
  wget -q -O - --no-check-certificate https://localhost:443
Atajo Imperativo CKA
Nunca codifiques manualmente en Base64 certificados multilínea en YAML en un examen: el comando imperativo kubectl create secret tls <nombre> --cert=... --key=... es 10 veces más rápido y libre de errores de sangrado.

Explicación Técnica: Los PersistentVolumes son recursos a nivel de clúster (no pertenecen a ningún namespace). La política Retain garantiza que cuando el PVC se elimine, el PV pasa al estado Released y los datos no se borran del disco físico.

  volumeMode: Filesystem
  accessModes:
    - ReadWriteOnce
  persistentVolumeReclaimPolicy: Retain
  storageClassName: manual
  hostPath:
    path: /mnt/k8s-data
    type: DirectoryOrCreate

← Volver al Enunciado

← Volver al Enunciado

Explicación Técnica: La directiva concurrencyPolicy acepta 3 valores: Allow (permite solapamiento), Forbid (si el anterior sigue activo, omite la nueva ejecución) y Replace (mata el anterior e inicia el nuevo).

          restartPolicy: OnFailure

            - name: backup
              image: busybox:1.36

Solución 9.1: Solución: Agente de Recolección de Logs de Nodo montando /var/log

← Volver al Enunciado

Explicación Técnica: Los DaemonSets utilizan un volumen hostPath para acceder a archivos del sistema de archivos local del nodo físico subyacente.

apiVersion: v1

  name: lab-daemonsets

  name: ds-node-log-collector
  namespace: lab-daemonsets

    matchLabels:
      app: node-logger

      labels:
        app: node-logger
    spec:
      volumes:

          hostPath:
            path: /var/log
            type: Directory
      containers:
        - name: log-collector
          image: busybox:1.36
          command:
            - /bin/sh
            - -c
            - "tail -n +1 -f /host/var/log/syslog || sleep 3600"

            - name: host-logs
              mountPath: /host/var/log

Solución 9.2: Solución: Tolerancias para Forzar Ejecución en Nodos del Control Plane

← Volver al Enunciado

Explicación Técnica: Para tolerar cualquier taint de tipo NoSchedule en el nodo master, se define una tolerancia con operator: Exists que empareje con las claves node-role.kubernetes.io/control-plane y la clave histórica node-role.kubernetes.io/master.

Manifiesto YAML con Tolerations:

apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: ds-security-agent
  namespace: lab-daemonsets
  labels:
    app: security-agent
spec:
  selector:
    matchLabels:
      app: security-agent
  template:
    metadata:
      labels:
        app: security-agent
    spec:
      tolerations:
        - key: node-role.kubernetes.io/control-plane
          operator: Exists
          effect: NoSchedule
        - key: node-role.kubernetes.io/master
          operator: Exists
          effect: NoSchedule
      containers:
        - name: agent
          image: alpine:3.19
          command: ["/bin/sh", "-c", "echo 'Seguridad activa en nodo'; sleep 3600"]

Validación:

kubectl apply -f ds-tolerations.yaml
# Comprobar que existe un Pod en cada nodo incluyendo el master
kubectl get pods -n lab-daemonsets -l app=security-agent -o wide

Solución 9.3: Solución: Actualización Controlada de DaemonSet (RollingUpdate vs OnDelete)

← Volver al Enunciado

Explicación Técnica: Si se usa updateStrategy: OnDelete, los Pods de los nodos no se actualizan hasta que el administrador los elimina manualmente. Con RollingUpdate (el valor por defecto moderno), Kubernetes destruye y recrea Pods nodo a nodo según maxUnavailable.

Comandos de Actualización:

# 1. Actualizar la imagen del DaemonSet
kubectl set image ds/ds-node-log-collector \
  log-collector=busybox:1.36.1 -n lab-daemonsets

# 2. Monitorear el progreso en tiempo real
kubectl rollout status ds/ds-node-log-collector -n lab-daemonsets

# 3. Comprobar que todos los Pods ejecutan la nueva versión
kubectl get pods -n lab-daemonsets -l app=node-logger -o jsonpath='{.items[*].spec.containers[*].image}'

Solución 11.3: Solución: Terminación TLS Segura en Ingress con Secret Asociado

← Volver al Enunciado

Explicación Técnica: La sección tls mapea hosts específicos a un Secret de tipo kubernetes.io/tls. El Ingress Controller se encarga del handshake SSL, descargando de esa tarea de cómputo a los microservicios backend.

Comandos y Manifiesto YAML:

# 1. Crear certificado SSL autofirmado
openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
  -keyout /tmp/tienda.key -out /tmp/tienda.crt -subj "/CN=tienda.example.com"

# 2. Crear Secret en el mismo namespace del Ingress
kubectl create secret tls sec-ingress-tls -n lab-ingress \
  --cert=/tmp/tienda.crt --key=/tmp/tienda.key

Manifiesto con TLS habilitado:

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: ingress-tls-secure
  namespace: lab-ingress
spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - tienda.example.com
      secretName: sec-ingress-tls
  rules:
    - host: tienda.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: svc-catalog
                port:
                  number: 80

Validación:

kubectl apply -f ingress-tls.yaml
curl -k -v --resolve tienda.example.com:443:127.0.0.1 https://tienda.example.com/

12. Soluciones Técnicas: RBAC: Control de Acceso Basado en Roles y Cuentas de Servicio

Namespace: lab-rbac

Solución 12.1: Solución: Creación de ServiceAccount Dedicada y Endurecimiento de Tokens

← Volver al Enunciado

Explicación Técnica: Por defecto, cada Pod monta automáticamente el token JWT de su ServiceAccount. Si un Pod sufre una vulnerabilidad de ejecución remota de código (RCE), el atacante podría utilizar dicho token para hablar con el API Server. Deshabilitarlo con automountServiceAccountToken: false mitiga este vector de ataque.

Manifiesto YAML:

apiVersion: v1
kind: Namespace
metadata:
  name: lab-rbac
---
apiVersion: v1
kind: ServiceAccount
metadata:
  name: sa-limited-app
  namespace: lab-rbac
automountServiceAccountToken: false
---
apiVersion: v1
kind: Pod
metadata:
  name: pod-secure-sa
  namespace: lab-rbac
spec:
  serviceAccountName: sa-limited-app
  containers:
    - name: app
      image: alpine:3.19
      command: ["/bin/sh", "-c", "sleep 3600"]

Validación:

kubectl apply -f sa-hardened.yaml
kubectl exec -n lab-rbac pod-secure-sa -- \
  ls -la /var/run/secrets/kubernetes.io/serviceaccount 2>&1
# Confirmar que la ruta no existe

Solución 12.2: Solución: Definición de Role con Privilegios Mínimos (Least Privilege)

← Volver al Enunciado

Explicación Técnica: Los Roles se circunscriben estrictamente a un namespace específico (a diferencia de los ClusterRoles que abarcan todo el clúster o recursos sin namespace como Nodos o PVs). Los sub-recursos (como pods/log o pods/exec) deben especificarse explícitamente.

Manifiesto YAML:

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: role-pod-viewer
  namespace: lab-rbac
rules:
  - apiGroups: [""] # "" indica el apiGroup core
    resources: ["pods", "pods/log"]
    verbs: ["get", "list", "watch"]
  - apiGroups: ["apps"]
    resources: ["deployments"]
    verbs: ["get", "list"]

Comando Imperativo Rápido (Truco CKA):

kubectl create role role-pod-viewer -n lab-rbac \
  --verb=get,list,watch --resource=pods,pods/log \
  --dry-run=client -o yaml > role.yaml

Solución 12.3: Solución: RoleBinding y Comprobación con kubectl auth can-i

← Volver al Enunciado

Explicación Técnica: El RoleBinding une el sujeto (usuario, grupo o ServiceAccount) con el Role deseado. El comando kubectl auth can-i permite validar autorizaciones impersonando a cualquier identidad del sistema mediante la sintaxis system:serviceaccount:<namespace>:<nombre-sa>.

Manifiesto YAML del RoleBinding:

apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: rb-pod-viewer-binding
  namespace: lab-rbac
subjects:
  - kind: ServiceAccount
    name: sa-limited-app
    namespace: lab-rbac
roleRef:
  kind: Role
  name: role-pod-viewer
  apiGroup: rbac.authorization.k8s.io

Auditoría de Permisos con kubectl auth can-i (Fundamental en CKA):

# 1. Aplicar RoleBinding
kubectl apply -f rb-viewer.yaml

# 2. Comprobar que PUEDE listar pods en lab-rbac -> Devuelve "yes"
kubectl auth can-i list pods -n lab-rbac \
  --as=system:serviceaccount:lab-rbac:sa-limited-app

# 3. Comprobar que NO PUEDE borrar pods en lab-rbac -> Devuelve "no"
kubectl auth can-i delete pods -n lab-rbac \
  --as=system:serviceaccount:lab-rbac:sa-limited-app

# 4. Comprobar que NO TIENE acceso en default -> Devuelve "no"
kubectl auth can-i list pods -n default \
  --as=system:serviceaccount:lab-rbac:sa-limited-app

Solución 13.1: Solución: Anatomía de un Chart, Creación y Depuración con helm template / lint

← Volver al Enunciado

Explicación Técnica: Un Helm Chart contiene metadatos (Chart.yaml), valores por defecto (values.yaml) y plantillas en templates/ que combinan sintaxis YAML con Go templating. helm lint valida buenas prácticas y helm template renderiza los YAML sin interactuar con la API de Kubernetes.

# 1. Crear namespace

rm -f my-webapp/templates/hpa.yaml \

# 4. Validar sintaxis estricta
helm lint my-webapp

# 5. Renderizar manifiestos para previsualización
helm template test-render my-webapp --set replicaCount=2

Solución 13.2: Solución: Instalación Parametrizada y Sobreescritura de Valores (--set y -f)

← Volver al Enunciado

Explicación Técnica: La jerarquía de valores en Helm sigue el principio de especificidad: los valores en values.yaml tienen la menor precedencia, sobreescritos por -f custom-values.yaml, y finalmente sobreescritos por flags individuales --set.

Archivo values-production.yaml:

replicaCount: 3
image:
  repository: nginx
  tag: "1.25-alpine"
resources:
  limits:
    memory: 128Mi
  requests:
    memory: 64Mi

Comando de Despliegue:

# Desplegar combinando archivo de valores y --set
helm install webapp-prod ./my-webapp \
  --namespace lab-helm \
  -f values-production.yaml \
  --set service.type=NodePort

# Comprobar la release en el clúster
helm list -n lab-helm
kubectl get pods -n lab-helm -l app.kubernetes.io/instance=webapp-prod

Solución 13.3: Solución: Gestión del Ciclo de Vida: helm upgrade, helm history y helm rollback

← Volver al Enunciado

Explicación Técnica: Helm guarda el estado de cada release en Secrets cifrados en el clúster (con el tipo helm.sh/release.v1). Esto permite que helm history conozca el historial completo de despliegues y pueda revertir cualquier cambio al instante con helm rollback.

Simulación de Fallo y Rollback:

# 1. Ejecutar upgrade con imagen inexistente
helm upgrade webapp-prod ./my-webapp -n lab-helm --set image.tag=v_error_99

# 2. Comprobar que los Pods fallan
kubectl get pods -n lab-helm

# 3. Consultar el historial de revisiones
helm history webapp-prod -n lab-helm
# Observar que la revisión 1 fue exitosa y la revisión 2 es la actual fallida

# 4. Revertir a la revisión 1
helm rollback webapp-prod 1 -n lab-helm

# 5. Confirmar que los Pods vuelven a estar operativos
kubectl get pods -n lab-helm
helm history webapp-prod -n lab-helm

14. Soluciones Técnicas: Kustomize: Personalización Declarativa sin Plantillas

Namespace: lab-kustomize

Solución 14.1: Solución: Capa Base con Mutación Automática de Metadatos (Labels y Prefijos)

← Volver al Enunciado

Explicación Técnica: Kustomize no necesita motor de plantillas: lee archivos YAML estándar de Kubernetes y aplica mutaciones sintácticas estructuradas a través de su archivo descriptor kustomization.yaml.

Estructura de Directorios:

base/
├── deployment.yaml
├── service.yaml
└── kustomization.yaml

Archivo base/kustomization.yaml:

apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization

namespace: lab-kustomize

namePrefix: dev-

commonLabels:
  project: auth-system
  managed-by: kustomize

resources:
  - deployment.yaml
  - service.yaml

Comandos de Validación:

# 1. Crear namespace
kubectl create namespace lab-kustomize

# 2. Renderizar y previsualizar sin aplicar
kubectl kustomize base/

# 3. Aplicar directamente en el clúster
kubectl apply -k base/
kubectl get all -n lab-kustomize -l project=auth-system

Solución 14.2: Solución: Generación Declarativa de ConfigMaps y Secrets con Hash de Contenido

← Volver al Enunciado

Explicación Técnica: Al generar un ConfigMap con hash en el nombre (ej. cm-app-props-k8h5f8mt4d), cualquier cambio en el archivo de origen produce un nuevo hash. Kustomize actualiza simultáneamente la referencia en el Deployment, provocando un RollingUpdate automático de los Pods.

Configuración en kustomization.yaml:

apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization

resources:
  - deployment.yaml

configMapGenerator:
  - name: cm-app-props
    files:
      - app.properties

Deployment que lo consume (referenciando el nombre base):

# En deployment.yaml sólo referenciamos el nombre base:
# Kustomize se encarga de reemplazarlo por el nombre con hash
volumes:
  - name: config-vol
    configMap:
      name: cm-app-props

Validación:

kubectl kustomize . | grep -A 5 "kind: ConfigMap"

Solución 14.3: Solución: Gestión Multi-Entorno con Overlays y Parches Estratégicos (patches)

← Volver al Enunciado

Explicación Técnica: Los overlays reutilizan la capa base y sólo declaran las diferencias (parches) correspondientes a cada entorno específico (desarrollo, staging o producción), eliminando la duplicación de código.

Estructura de Overlays:

k8s-app/
├── base/
│   ├── deployment.yaml
│   └── kustomization.yaml
└── overlays/
    ├── dev/
    │   └── kustomization.yaml
    └── prod/
        ├── kustomization.yaml
        └── patch-prod.yaml

Archivo overlays/prod/patch-prod.yaml:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-users
spec:
  replicas: 4
  template:
    spec:
      containers:
        - name: api
          resources:
            requests:
              memory: "128Mi"
              cpu: "100m"
            limits:
              memory: "256Mi"
              cpu: "250m"

Archivo overlays/prod/kustomization.yaml:

apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization

resources:
  - ../../base

namePrefix: prod-

patches:
  - path: patch-prod.yaml

Despliegue y Validación:

# 1. Aplicar overlay de producción
kubectl apply -k overlays/prod/

# 2. Comprobar que existen 4 réplicas con el prefijo prod-
kubectl get deployment -n lab-kustomize prod-api-users
